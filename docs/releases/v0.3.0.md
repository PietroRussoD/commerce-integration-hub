# v0.3.0 - Idempotent Kafka Order Processing

`v0.3.0` closes the first asynchronous order-processing loop. The Integration
Core now consumes its published `OrderReceived.v1` events, applies each business
effect once, transitions the order to `READY`, and publishes a distinct
`OrderReady.v1` event for downstream integrations.

## Highlights

- A transactional inbox deduplicates deliveries by consumer name and stable
  event ID.
- Processing moves orders through `RECEIVED -> PROCESSING -> READY` with
  optimistic status updates.
- Each initial execution records a durable processing attempt and appends
  `PROCESSING_STARTED` and `PROCESSING_SUCCEEDED` timeline entries.
- The inbox entry, state transitions, attempt, timeline, and pending
  `OrderReady.v1` outbox event commit in one PostgreSQL transaction.
- Duplicate Kafka deliveries are acknowledged without repeating processing
  effects.
- Invalid events and permanent processing rejections bypass retries, while
  transient failures use bounded retries before dead-letter routing.
- `OrderReceived.v1`, `OrderReady.v1`, and dead-letter records use separate
  topics.
- Redpanda Console is included in the local Compose environment for inspecting
  topics, records, consumer groups, and lag.

## Processing Semantics

Kafka delivery remains at least once. The consumer therefore treats the stable
event ID as its idempotency key and records it in PostgreSQL inside the same
transaction as the processing effects. A failure rolls the complete transaction
back, allowing Kafka retry to execute the operation again. A committed
transaction followed by an uncommitted Kafka offset produces a duplicate
delivery, which the inbox acknowledges without repeating the effects.

The initial processing implementation models a successful internal validation
step rather than payment, inventory, fulfilment, or another external business
workflow. Operator inspection and audited replay of failed deliveries remain
outside this release.

## Upgrade Notes

Flyway adds the transactional consumer inbox, expanded order and timeline
statuses, and processing-attempt persistence. Back up production data before a
real deployment; this portfolio release does not provide a tested downgrade
procedure.
