# v1.2.0 - A Local Kubernetes Environment With Failure Tests

`v1.2.0` adds an optional local Kubernetes environment for the Hub, built to
exercise it under conditions Docker Compose cannot reproduce: replicas on
different nodes, database failover, a service mesh, and network faults. Compose
remains the simplest way to run the project. No HTTP or event contract changes.

## Highlights

- **A reproducible cluster** (`scripts/k8s/up.sh`): kind with one control-plane
  and two worker nodes, the Helm chart `deploy/charts/commerce-integration-hub`
  (two replicas of the Core and the Gateway, the provider simulator, the Gateway
  migration as a Job, probes, resource limits, non-root containers with a
  read-only root filesystem), CloudNativePG with a primary and a replica for each
  service, and the Redpanda operator with the four topics as resources. Each
  replica names its workers after its own pod.
- **Failure tests** (`scripts/k8s/verify-failures.sh`): 60 webhooks are sent
  while pods, a database primary, the Core's calls, a Gateway pod holding leases,
  the broker, or a node fail; both databases are then checked for losses and
  duplicates. See the [failure runbook](../runbooks/failures.md).
- **Synchronous replication** for both PostgreSQL clusters, chosen from
  measurements ([ADR 0022](../decisions/0022-synchronous-postgresql-replication.md)).
- **An ambient service mesh** (Istio, [ADR 0023](../decisions/0023-ambient-mesh-and-application-retries.md)):
  mutual TLS in the application namespace, authorization by workload identity, a
  Gateway API ingress that exposes only the APIs, and a waypoint in front of the
  Core with an explicit no-retry policy, so that retries stay in the applications.
- **Alerts** (15 rules, each tested with `promtool` and documented in the
  [alert runbook](../runbooks/alerts.md)), Alertmanager without receivers, and
  an observability stack for the cluster (Prometheus, Alertmanager, the
  OpenTelemetry Collector, Jaeger, Grafana).
- **In the Core:** gauges for the outbox backlog, the age of its oldest event and
  its terminally failed events, and JDBC connect and socket timeouts.

## What the failure tests found

- With the Core's database primary unreachable but no connection closed, the
  Core's threads waited on it for ever: orders stayed `RECEIVED` until the pods
  were restarted. The JDBC timeouts fix it. In a control run without them, 9 of
  60 orders had reached `READY` after four minutes; with them, all 60 did in
  about 105 seconds, with no pod restarted.
- The outbox publishes about ten events a second with two replicas, so a burst of
  thousands of orders queues for minutes. Nothing is lost; the new age gauge and
  alert make the delay visible.
- With the mesh's default settings, a call answered `503` and a call whose
  connection is dropped each reached a stand-in server once: the waypoint did not
  retry them. The no-retry policy is explicit so that the rule does not rest on
  that default.
- Where targets are discovered from pods, a pod that disappears leaves no `up`
  series, so a new alert covers an application with no replica at all.

## Verification

- The Core's full `./mvnw verify` passed locally with 188 unit and 166
  integration tests after the outbox gauges were added. The JDBC timeouts are in
  the production profile only and were verified in the cluster, not by that run.
- The alert rules pass `promtool test rules` (21 test groups); the Alertmanager
  and Prometheus configurations pass `amtool check-config` and
  `promtool check config`.
- `scripts/k8s/verify-failures.sh` passed for `pods`, `core-primary`,
  `gateway-primary`, `core-slow`, `core-errors`, `gateway-lease`, `broker` and
  `core-db-blackhole` on a three-node cluster on one machine; the `node`
  scenario found the defect described above.
- `scripts/k8s/verify-mesh.sh` and `scripts/k8s/verify-alerts.sh` passed: the
  mesh admits only the allowed callers, and two real failures (no Core replica,
  a rollout of a missing image) reach Alertmanager.
- Traces of an order still span the Gateway and the Core inside the mesh.

## Operational Boundary

The environment is local. It has no cloud deployment, no public endpoint, no
backup or disaster recovery, and no load test; the alert thresholds are
demonstrative. Alertmanager sends alerts nowhere. The published container images
are `linux/amd64` only, so the environment builds its own for the machine.
Traffic to PostgreSQL and Redpanda is not encrypted by the mesh, the Gateway's
database calls have no explicit timeouts, and the failure tests ran on one
machine, one failure at a time. PostgreSQL remains authoritative for orders.
