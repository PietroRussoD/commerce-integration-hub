# v0.2.0 - Reliable Kafka Outbox Publication

`v0.2.0` turns the transactional outbox records introduced in `v0.1.0` into a
working Kafka publication pipeline. It adds bounded, recoverable background
dispatch while preserving short database transactions and explicit
at-least-once delivery semantics.

## Highlights

- Workers atomically claim disjoint batches with PostgreSQL `SKIP LOCKED`.
- Random fencing tokens prevent stale workers from completing newer claims.
- Scheduled dispatch publishes structured `OrderReceived` version 1 events.
- Kafka records use stable aggregate keys and routing headers derived from the
  authoritative event envelope.
- Retryable failures use bounded exponential backoff with equal jitter;
  permanent and exhausted failures move to a durable terminal state.
- A separate scheduler recovers expired claims after interrupted processing.
- The producer uses `acks=all`, Kafka idempotence, and bounded request,
  delivery, and application timeouts.
- Prometheus exposes bounded dispatch outcomes, recovered claims, and scheduler
  execution metrics.

## Local Environment

Docker Compose now starts PostgreSQL, Redpanda, and the Integration Core. A
one-shot initializer creates `integration.order.received.v1` with three
partitions. Both database and broker data use named volumes, and service startup
is gated by health and topic initialization.

The documented demo covers credential provisioning, authenticated order
ingestion, outbox dispatch, and inspection of the resulting Kafka record.

## Delivery Semantics

Publication is intentionally at least once. A process can stop after the broker
acknowledges a record but before PostgreSQL records `PUBLISHED`; a later worker
may therefore publish the same stable event ID again. Downstream consumers must
deduplicate by event ID before applying business effects.

Event consumption, consumer deduplication, dead-letter operations, and audited
operator replay are outside this release. See
[current limitations](../limitations.md) for the complete boundary.

## Upgrade Notes

Flyway applies the outbox fencing and terminal-failure migrations added after
`v0.1.0`. Back up production data before any real deployment; this portfolio
release does not provide a tested downgrade procedure.
