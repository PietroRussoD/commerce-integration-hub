# v0.1.0 - Reliable Canonical Order Ingestion

`v0.1.0` is the first public-quality vertical slice of Commerce Integration
Hub. It establishes authenticated, idempotent order ingestion with durable
PostgreSQL persistence and an atomic transactional outbox boundary.

## Highlights

- `POST /api/v1/orders` validates and persists currency-aware orders.
- `GET /api/v1/orders/{id}` returns orders owned by the authenticated source.
- Equivalent submissions return the existing order; conflicting content for
  the same source identity is rejected without overwriting canonical data.
- Orders, line items, the `ORDER_RECEIVED` timeline entry, and the pending
  `OrderReceived` outbox event commit in one database transaction.
- Per-source API keys support secure provisioning, expiry, revocation, and
  pepper rotation while storing only HMAC values.
- Problem Details and correlation IDs provide consistent error and diagnostic
  behavior.

## Engineering Baseline

- Kotlin and Quarkus with a Java 21 compilation target;
- PostgreSQL schema evolution through Flyway and type-safe access through jOOQ;
- generated and committed OpenAPI YAML and JSON plus runtime Swagger UI;
- separate unit and PostgreSQL integration tests with combined JaCoCo coverage;
- Docker Compose local demo with health checks;
- CycloneDX SBOM, Gitleaks history scanning, Trivy final-image scanning, and
  weekly Dependabot updates.

## Verification

A clean clone passed `./mvnw clean verify` with 128 tests. The documented local
demo produced:

- `201 Created` for first ingestion;
- `200 OK` with the same order for an equivalent replay;
- `409 Conflict` for different content with the same source identity;
- `200 OK` for an authenticated read;
- one durable order, timeline entry, and outbox event after all submissions.

Gitleaks found no secret in the complete Git history, and Trivy reported no
`HIGH` or `CRITICAL` vulnerability in the final JVM image at release rehearsal.

## Running the Release

Follow the [local demo](../../services/integration-core/README.md#local-demo) to
build the service, start PostgreSQL, provision a source credential, and exercise
the ingestion behavior.

This is the initial release, so there is no upgrade procedure from an earlier
version. Database changes are owned by the ordered Flyway migrations.

See [current limitations](../limitations.md) for capabilities deliberately left
outside this release.
